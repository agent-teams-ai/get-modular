# Фундамент модульности: сводка 12 ревью (2026-10-01)

По каждой теме три независимых разбора: `*-industry.md` (лучшее из индустрии), `*-minimal.md`
(минимально достаточное), `*-scale.md` (стресс-тест на 3 года роста). Ниже — где они сошлись,
где разошлись и рекомендация. Оценки — надёжность/уверенность из 10.

## 1. Эволюция контрактов capability

**Сошлись все трое:** ломающее изменение = новый `capabilityId` (major в id: `acme/logger/v2`);
это уже работает на опубликованном 0.2.0 (проверено экспериментами); адаптер между линиями —
обычный модуль; semver-диапазонов и конверторов в Core нет. Сегодняшний `token` смысла не несёт:
в AR один token на 8 и на 10 capability.

**Разошлись:** минималист убирает `compatibility`/token совсем (9/8); двое других заменяют его
монотонной ревизией: провайдер объявляет `revision`, слот — `minimum`, проверка `revision >= minimum`
(9/8 и 8/7). Ревизия ловит «провайдер без нового метода» у плагина без общей TS-проверки.

**Находки:** TS молча пропускает ломающее изменение при method-синтаксисе (бивариантность) — нужен
lint на property-функции; главный риск — цена нового поколения квалификационных артефактов
(`familyVersion` в 94 файлах), поэтому все wire-изменения собрать в одно поколение.

**Рекомендация:** версия в id + ревизия, одним wire-поколением Core/Assembly 0.3.0; сразу —
ADR, правила в Consumer Module Standard, отдельный id/token на каждый контракт в AR.

## 2. Пространства имён

**Сошлись все трое:** Core не авторизует (злонамеренный плагин он всё равно не остановит);
права выдаёт Host/Extension Foundation; правила формата id в стандарте; capability принадлежит
владельцу контракта, а не провайдеру; id неизменяемы, без алиасов и повторного использования;
переименовать AR сейчас (~20 деклараций).

**Находки в AR:** три разных корня имён в одном графе; один id `agent-runtime/runtime-host` у двух
деклараций; `owner.authority` не совпадает с префиксом. В тексте GM: GM-REQ-004 разрешает
авто-привязку при единственном провайдере (риск dependency confusion); плагин с id встроенного модуля
роняет весь Host.

**Разошлись:** только документы (8/8) / + чистая функция `checkNamespaces` в Core без вызова из
компилятора, ~80 строк (8/7) / + три эксклюзивных гранта на плагин и общий grant-checker вместе с
первым Host, который грузит плагины (8/8).

**Рекомендация:** правила + переименование AR сейчас; `checkNamespaces` как чистый хелпер;
grant-checker — с первым плагинным Host; авто-привязку для плагинов запретить.

## 3. Динамические модули

**Сошлись все трое:** живой граф с заменой отдельного модуля в GM — нет (4–5/10); замена = собрать
новый экземпляр, переключить указатель у владельца, закрыть старый (как Erlang, VS Code); экземпляры
на сессию/tenant = вложенный run под `child()`; Core и kernel не меняются; выгрузку кода в процессе
не обещаем (ESM в Node не выгружается).

**Найден дефект в дизайне resources (подтвердили двое):** `scoped(parent, …)` берёт родителя в момент
`bindFactory`; одна подготовленная сборка для двух сессий → закрытие сессии 1 закрывает ресурсы
сессии 2. Ещё: передать данные в run нельзя (через замыкание параллельные run путают данные),
подграф не видит провайдеров родителя, prepare ~27× дороже run.

**Разошлись:** ничего не менять в GM, пересобирать на экземпляр (9/8) / `RunOptions.context` или
`run({ owner })` в Assembly, 25–50 строк (8/7) / «ячейки»: `bindInput` + `run({signal, owner, inputs})`
сразу (8/7).

**Рекомендация:** модель «экземпляры вместо мутации» + маленькая правка Assembly `run({ owner })`
сейчас (чинит дефект `scoped`, до релиза resources); типизированные входы run — по первому реальному
триггеру; узкий контекст, не мешок сервисов.

## 4. Тестирование модулей

**Сошлись все трое:** никаких TestBed, авто-моков и DSL; фейки типизируются через
`FactoryDependencies` (компилятор ловит дрейф — проверено); фейк и контракт-набор держит владелец
capability, и фейк проходит тот же набор, что и реальная реализация; smoke «собрать → упасть на
каждом модуле → закрыть → complete» дешёвый (500 модулей ≈ 0,27 с); smoke не доказывает реальные
адаптеры; `complete` ≠ физическое освобождение.

**Находки в AR:** 638 строк `as never` в 157 тестовых файлах отключают проверку типов фейков;
35 скопированных фикстур, одна уже разошлась; утёкший handle оставляет тест зелёным, а
`--test-force-exit` его прячет.

**Разошлись:** только правила + тип `ModuleFactory`, пакет после трёх копий (8/8) / тонкий
`@get-modular/testing` ~200 строк (8/7) / тонкий `@get-modular/conformance` (имя уже
зарезервировано ADR-0003) ~300 строк: `isolate`, `smoke`, `runContractSuite`, `guardHandles` (8/7).

**Рекомендация:** по правилу «сразу библиотекой» — тонкий `@get-modular/conformance`: `isolate`,
`smoke`, `runContractSuite`, `guardHandles` + правила про фейки у владельца контракта. Без
`expectBindings` (конфликтует с требованием независимого эталона).

## Решения владельца (2026-10-01)

1. **Контракты: ревизия, но без `/v2` в id.** Одна линия на контракт, без параллельных версий.
   Провайдер объявляет `revision` (растёт с каждым изменением) и `compatibleFrom` (самая старая
   ревизия потребителя, которую он ещё поддерживает). Слот объявляет `revision`, под которую собран
   потребитель. Привязка разрешена, если `compatibleFrom <= слот.revision <= провайдер.revision`.
   Ломающее изменение делается на месте: `revision` растёт, `compatibleFrom` поднимается до неё,
   старые потребители получают понятную ошибку и обновляются по гайду миграции. Token убираем.
   Одно wire-поколение Core/Assembly 0.3.0. Аналог: Android minSdk/API level.
   Надёжность 8/10, уверенность 7/10.
2. **Пространства имён:** правила + `checkNamespaces` + гранты у Host (рекомендация принята).
3. **Динамические модули:** направление «экземпляры + `run({ owner })`» нравится, но владелец
   попросил ещё два исследования (Opus 5.5): `dynamic-modules-final-a.md` (индустрия) и
   `dynamic-modules-final-b.md` (реальные потребители и замеры). Окончательный выбор после них.
4. **Тесты:** тонкий `@get-modular/conformance` (рекомендация принята).

Вопросы плана реализации ресурсов, решённые по умолчанию (рекомендованные варианты):
А — пин CMS в `sdk-growth` сверять с замороженными байтами через `git show`;
Б — дренаж и доказательство остановки остаются шагом Host до закрытия scope, ошибка самого
`feature.dispose` принимается по Q1; предпосылку «PA после codex» AR выражает slot'ом, если она
реальна; В — async `dispose` в Darwin принимаем (breaking разрешён), рост записей сессий —
незавершённая работа до хука конца сессии; Г — ждёт итог исследований по динамике.

## Решения владельца после финальных исследований и критики плана (2026-10-01)

- **Динамика:** `run({ signal, owner, inputs })` + `bindInput` в Assembly 0.3.0, заготовка сборки
  один раз, каждый запуск со своим scope и входами; Core и kernel без изменений; опция
  `child({ order: "concurrent" })` для массового закрытия сессий (`dynamic-modules-final-a.md`,
  `dynamic-modules-final-b.md`).
- **Релизы — два поезда:** 0.3.0 = Assembly (owner, inputs) + Core (только номер версии) +
  resources 0.1.0 (`scoped(name, factory)`) + conformance 0.1.0; 0.4.0 = wire-поколение контрактов
  (revision/compatibleFrom) + хелпер имён.
- **abandon — только для вызывающего:** он сразу получает отчёт, закрытие идёт дальше по порядку,
  остальные ждущие (включая родителя) продолжают ждать; вне порядка ничего не стартует.
- Критика плана реализации: `impl-plan-critique-{semantics,integration,coherence}.md`; правки
  внесены в `../module-resource-scopes-implementation-plan-2026-10-01.md`.

## Общее

- Все изменения wire-формата (контракты, при необходимости namespace) — одним поколением Core 0.3.0,
  чтобы платить цену квалификационных артефактов один раз.
- Assembly 0.3.0: `run({ owner })`, тип `ModuleFactory`.
- resources: `scoped(name, factory)` берёт родителя из контекста run.
- Оценка готовности после этого: ~75–80% (сейчас ~40%).
