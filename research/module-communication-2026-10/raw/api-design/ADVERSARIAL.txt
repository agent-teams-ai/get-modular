F1 [P1, уверенность 8] Срезы по вариантности защищены только при сравнении алиас-к-алиасу
VERIFIED: b-snapshot/api.d.ts:95 "export type ReadonlyStore<out V> = {".
VERIFIED: RATIONALE.txt:112 "Evidence: MEASURED, type-tests (slice from wide passes; reverse, unrelated, same key with
another type fail)". Все эти тесты сравнивают ReadonlyStore<A> с ReadonlyStore<B> напрямую.
VERIFIED: RATIONALE.txt:95-96 "Invariant to keep: Store must never gain watch or load, or this protection disappears."
MEASURED (critic-probes/v1-structural.ts, текущий B, tsc7 7.0.2 и TS 5.8.3): ReadonlyStore<App> молча
присваивается всем этим типам:
  - Readonly<ReadonlyStore<Unrelated>> и Readonly<ReadonlyStore<WrongType>>;
  - Pick<ReadonlyStore<Unrelated>, "watch"> и Pick<ReadonlyStore<WrongType>, "read">;
  - свой порт { readonly read: ReadonlyStore<WrongType>["read"]; readonly watch: ReadonlyStore<WrongType>["watch"] };
  - типы членов ReadonlyStore<WrongType>["read"] и ReadonlyStore<Unrelated>["watch"].
Пересечение, Promise<> и массив ловятся, но только пока стоит `out V`: в контроле без аннотации tsc7 пропускает
и их.
MEASURED на исходниках GM origin/main с implement<C>()(declaration, factory, scoped) (critic-adv/gm05/p05.ts):
ReadonlyStore<WrongSlice> ловится (строка 46), а Pick<ReadonlyStore<WrongSlice>, "read"> нет (строка 53,
"Unused '@ts-expect-error'" на обоих компиляторах).
Почему это реально: CMS прямо учит писать свой порт приложения, который порт фичи удовлетворяет структурно.
common-assembly.md:675 (origin/main): "The use case types what it needs with its own port; the store feature's port
satisfies it structurally." Агент, который пишет application/ports для greeter, напишет Pick<ReadonlyStore<...>, "read">.
Если тип значения у владельца поменяется, код соберётся и получит в рантайме другой тип.
MEASURED, минимальный репро: critic-adv/sig/tsc7-variance-repro.ts. Без аннотаций TS 5.8.3 отвергает
R1<App> -> R1<Wrong> (TS2322 x2), а tsc7 7.0.2 принимает. Это расхождение TS7 с TS5. Похоже на баг tsc7
(ASSUMPTION). Репортить ли его в typescript-go, решает владелец; я ничего не публиковал.

Моё предложение: тип-маркер записи, только на уровне типов, как уже сделаны бренды.
  declare const storeValue: unique symbol;
  ReadonlyStore<out V> = { readonly [storeValue]: V; read; watch; load }
  Snapshot<V, K> и SnapshotOf<V> = { ...; readonly [storeValue]: V }
Файл: critic-adv/api/critic-variants/b-marker2/api.d.ts. MEASURED на обоих компиляторах:
  - b-snapshot/type-tests.ts: все 34 ожидания выполнены, лишних ошибок нет;
  - probes/p5-gm-contracts.b.ts и probes/p3-variance-controls.ts проходят;
  - то же самое БЕЗ `out V` (critic-variants/b-marker2-noout): все проверки проходят и на tsc7. Аннотация перестаёт
    быть несущей, и риск раздела 7 RATIONALE (недокументированное поведение) снимается;
  - v1-structural: Readonly<>, Pick<"read">, тип члена read и свой порт с read теперь отвергаются. Остались только
    порты из одного watch: Pick<..., "watch"> и ReadonlyStore<X>["watch"]. Практический риск низкий, потому что без
    read у такого порта нет своих снимков;
  - p05 на GM main: Pick<ReadonlyStore<WrongSlice>, "read"> теперь отвергается;
  - critic-probes/leak.ts: даже если Store получит watch и load, отдать store вместо readonly() не скомпилируется
    (TS2741). Инвариант RATIONALE.txt:95-96 перестаёт быть случайным.
Побочный эффект (MEASURED, critic-probes/slice-to-wide.ts): снимок, прочитанный через фасет-срез, больше нельзя
передать в watch широкого фасета того же store (TS2345). По-моему, это приемлемо: каждый фасет следует за своими снимками.
Плюс в README одна строка: "тип зависимости пишите только как ReadonlyStore<Slice>; Pick, Omit и типы членов
не используйте". Пробы v1-structural добавить в CI пакета. Запасной вариант RATIONALE.txt:293 ("type the snapshot
without the constraint") хуже: он теряет отказ на этапе компиляции.

F2 [P1, уверенность 8] Правило 7 видения нарушено в README и не реализовано в API
VERIFIED: b-snapshot/README.md:38 "Never write, in `onChange`, to the store you are watching. Ask its owner through a
command port instead."
VERIFIED: AGENTS.md:106 "Handlers are synchronous and never write what they were notified about, directly or through
a command. No echo."
VERIFIED: AGENTS.md:107 "Changes made during delivery are queued in order; a runaway cascade fails with a coded error."
VERIFIED: PRACTICES.md:235 (F2) "`Gap`: a cascade guard; `Proposed` mechanism (observation)".
VERIFIED: в ObservationErrorCode (api.d.ts:162-173) кода для каскада нет. В стабе (runtime/core.ts:220-234)
защиты нет.
1) Фраза README:38 естественно читается "в onChange вместо set позови командный порт владельца". Это и есть
   эхо через команду. В прогонах агенты так не делали (VERIFIED по g-hierarchy в runs/r*-b-*), но задачи
   их к этому и не подталкивали. ASSUMPTION: агенты будут следовать тексту буквально.
2) Пинг-понг через задачи (A->B->A через команды или производные store) бесконечно крутит CPU и молчит.
Моё предложение: переписать README:38 так: "A handler never changes what it was notified about, neither with set
nor through a command port. Change requests come from user actions and other inputs, through the owner's command
port." В ADR зафиксировать механизм: глубина каскада на уровне пакета, общая для всех store (а позже и событий).
set внутри доставки ставится в очередь с глубиной d+1, при превышении порога код вида observation.delivery.cascade.
Порог нужно согласовать с законными цепочками производных store (Home Assistant держит 10 000). В README добавить
ещё правило 5: не кодировать одноразовые события в ключах store, потому что коалесцирование их теряет
(AGENTS.md:94-97).

F4 [P1, уверенность 6] Лимит maxWatchers общий на store, а не на подписчика
VERIFIED: api.d.ts:154 "Live subscriptions (`watch` plus `load`) this store accepts. Default 1024; one more throws
`observation.watchers.limit`." RATIONALE.txt:69 "Owner decision 2026-10-16: the 1024 default stays."
Решение владельца касается значения по умолчанию. Здесь речь о гранулярности.
1) Радиус поражения (ASSUMPTION по коду runtime/core.ts:250, MEASURED в R5 только для одного модуля): модуль A
   с утечкой (сгенерированные имена в долгоживущем scope) набирает 1024 подписки. После этого watch невиновного
   модуля B в его фабрике бросает watchers.limit. Сообщение называет только store, а не того, кто держит подписки.
2) Динамические экземпляры: 200 сессий по 6 модулей, следящих за settings, дают 1200 подписок. Ошибка появляется
   только под реальной нагрузкой, в тестах её нет.
3) Поведение агентов (VERIFIED): runs/r3-b-snapshot-small-1/h-requests.ts:5 "a watch per ticker would count
   against the store's watcher limit" и r3-b-snapshot-small-2/h-requests.ts:6 то же. Теперь README.md:58-67 прямо
   направляет на ручной fan-out "when many pieces may be open at once (hundreds or more)". Автор модуля не может
   знать, сколько подписок держат на этом store ДРУГИЕ модули. Каждый модуль переизобретает изоляцию ошибок,
   которую библиотека уже даёт, и F11 показывает, что это делают с ошибками.
Вопрос владельцу Q1 (раздел 9).

F5 [P1, уверенность 7] Срезы через контракты не масштабируются ни в одной из двух форм
VERIFIED: README.md:4-5 "typed with their own slice (`ReadonlyStore<{ readonly theme: string }>`), never with the app's
whole settings type."
VERIFIED: probes/p5-gm-contracts.b.ts:10 и :33. Срез оформлен контрактом потребителя
("acme/logger/settings"), а владелец его provides: "provides: [LoggingSettingsContract.provide()]".
Форма 1, контракт потребителя: владелец settings объявляет provides и строку capability на каждого потребителя и
импортирует их пакеты контрактов. Получается центральный список и инверсия зависимости.
AGENTS.md:127-128: "A plugin never edits the Host's list". Плагин так вообще не может получить свой срез.
Форма 2, один широкий контракт ReadonlyStore<AppSettings>: common-assembly.md:575 "Raise `revision` with every change
of the value type, additive changes included" и :578 "a provider and every consumer of a capability use the same
revision". Каждый новый ключ настроек означает lockstep-релиз всех потребителей и ломает все плагины.
MEASURED (critic-adv/gm05/p05.ts): форма 2 с сужением в слое приложения работает на implement 0.5.0, но опирается
на сравнение, у которого есть дыра из F1.
Вопрос владельцу Q2 (раздел 9).

F6 [P2, уверенность 7] Закрытие источника: удержание памяти, тишина и read после close
MEASURED (critic-adv/api/runtime-b/critic-retention.test.ts, resources с origin/main): 50 store закрыты через close(),
а долгоживущий scope подписчика ещё открыт. Результат: "closed stores whose values are still reachable: 50/50;
handlers still reachable: 50/50". После закрытия scope подписчика стало 0/50. Причина VERIFIED в runtime/core.ts:307:
запись resources.use({ [Symbol.dispose]: registration.detach }, "watch:<name>") остаётся в scope подписчика и держит
замыкание с движком и обработчиком.
VERIFIED: RATIONALE.txt:103 "a closed store keeps no handler". Тест runtime-b/probes.test.ts:105 назван "even if the
subscriber scope is never closed", но :111 делает scope недостижимым ("dropped without close"). Заявление шире,
чем проба.
VERIFIED: api.d.ts:119-120 "then `set`, `watch` and `load` throw `observation.store.closed`". read продолжает
работать (runtime/core.ts:441-444), а PRACTICES.md:209 (E6) предлагает "`read` and `watch` on a closed store throw a
coded error". Подписчик никак не узнаёт о закрытии источника и молча показывает старые данные. Для поколений
плагинов (правило 11) это прямой сценарий.
При статической композиции LIFO закрывает потребителей раньше владельца, так что проблема только в close() посреди
жизни и в динамике (ASSUMPTION).
Моё предложение: реализовать watch как child-scope или очищать замыкания при detach, чтобы закрытый store не
удерживался; read после close бросает observation.store.closed. Политика уведомления: вопрос Q3. Публичный
Store.close() дублирует закрытие через resources. Подумать, нужен ли он вообще.

F10 [P2, уверенность 6] observation.scope.closing против resources.scope.closed
VERIFIED: api.d.ts:168 и README.md:51-53. resources README (origin/main):109 "`resources.scope.closed` | `setup`,
`use` or `child` after a close request".
Одно состояние, закрывающийся scope, получает два кода в двух пакетах, а позже третий от событий. Отдельный случай

3. Эволюция: что сломается
--------------------------
- События (createEvent, emit, subscribe). Спецификация { resources, name, on* } переиспользуется. Ломка
  неизбежна, если не переименовать сейчас то, что перечислено в F8. Защиту от каскада (F2) делать на уровне пакета,
  общей для store и событий, иначе её придётся переделывать.
- Плагины и динамические экземпляры. Фасет передаётся как input-порт: это frozen-объект с функциями, правилам
  CMS о портах соответствует. Риски: F4 (лимит под нагрузкой), F6 (смена поколения: тишина и удержание памяти),
  F8 (нет пути в отчёте), F5 (плагин не может получить контракт-срез потребителя).
  Владелец-sink reportError при плагинах инвертирует доверие: если Host следит за store плагина, ошибки
  обработчиков Host вместе с cause уходят в reportError плагина, и плагин может их заглушить (ASSUMPTION; для
  доверенного in-process кода допустимо, но в ADR это надо назвать).
- Проекция readonly(keys) добавляется аддитивно, необязательным параметром. С маркером F1 тип проекции
  ReadonlyStore<Pick<V,K>> согласован автоматически.
- Подписка на несколько store сразу. Методная форма её не выражает, понадобится вторая форма. Я проверил
  свободную функцию watch(snapshotOrTuple, spec) (critic-variants/b-free, MEASURED: кортеж [theme, rate] типизируется
  на обоих компиляторах). Но рекомендовать её не стану: снимок становится capability, и подписку можно оформить на
  store, к которому нет слота (правило 2). Методная форма в этом смысле герметична. Если делать мульти-store,
  то формой с явными парами (фасет, снимок). Тогда сразу надо решить, куда идёт ошибка обработчика, следящего за
  двумя владельцами с двумя reportError. Это единственный настоящий "угол" текущей модели ошибок.
- Селекторы и производные значения. Необязательный select с выводом типа onChange добавляется аддитивно
  (перегрузка). Производный store уже работает рецептом. Каждый шаг даёт ещё одну задачу задержки, и с защитой от
  каскада (F2) глубина цепочки производных должна укладываться в порог.
Аддитивно ломкой станет одно: если позже захочется ОБЯЗАТЕЛЬНЫЙ обработчик закрытия источника (в духе
обязательных onError и onLoading). Это ломает каждый вызов watch. Отсюда Q3 сейчас.

10. Вопросы владельцу
---------------------
Q1. Где считать лимит подписок?
  1) (Recommended) Лимит на scope подписчика (например, 64 на store в одном resources) плюс высокий страховочный
     лимит на store, который задаёт владелец. Ошибка называет верхние scope по пути (нужен Resources.path).
     Утечка падает в своём модуле, экземпляры масштабируются. Надёжность 8, уверенность 6.
  2) Оставить общий лимит 1024 на store, но ошибка называет держателей, а README требует от владельца store,
     которым пользуются экземпляры, задать maxWatchers явно. Надёжность 6, уверенность 7.
  3) Без жёсткого лимита: только счётчики и предупреждение. Надёжность 4, уверенность 7.

Q2. Как модуль получает свой срез через контракты на сотнях модулей и с плагинами?
  1) (Recommended) Владелец публикует несколько контрактов по смысловым областям (theme, logging, region...) и
     отдаёт один и тот же фасет под каждым. Потребитель берёт контракт своей области и сужает дальше в своём порте
     ReadonlyStore<Slice> (с маркером F1). Ревизия растёт только у затронутой области, центрального списка
     потребителей нет, плагины получают контракты Host. Надёжность 8, уверенность 6.
  2) Один широкий контракт ReadonlyStore<AppSettings> и сужение у потребителя: каждый новый ключ даёт lockstep-
     ревизию у всех и ломает плагины. Надёжность 6, уверенность 7.
  3) Контракт среза на каждого потребителя, который владелец provides (как probes/p5): центральный список и
     инверсия зависимости, плагинам недоступно. Надёжность 5, уверенность 7.

Q3. Что видит подписчик, когда его источник закрылся раньше него?
  1) (Recommended) Никакого нового обработчика. Закрытие store с живыми чужими подписками освобождает их сторону
     (без удержания памяти), отправляет один кодированный отчёт на подписку (например, observation.source.closed)
     в reportError, а read после закрытия бросает observation.store.closed. При статической композиции этого не
     бывает, в динамике это громко. Надёжность 7, уверенность 6.
  2) Обязательный onSourceClosed в WatchSpec и LoadSpec уже сейчас: подписчик решает сам (показать
     "недоступно", переподписаться). Надёжность 8, уверенность 4 (шаблонный код почти всегда не нужен).
  3) Отложить и позже добавить необязательный обработчик: до тех пор тишина и удержание памяти, а позже
     обязательный станет ломкой. Надёжность 5, уверенность 6.
