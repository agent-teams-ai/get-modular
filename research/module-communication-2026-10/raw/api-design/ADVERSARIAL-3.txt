M1 [P0, уверенность 9] Контекст доставки утекает в работу, которая переживает обработчик
VERIFIED:
  - runtime/core.ts:123-129 берёт AsyncLocalStorage через process.getBuiltinModule;
  - core.ts:339 запускает каждый обработчик в asyncContext.run;
  - core.ts:620-634 считает эхом любой коммит в этом контексте.
AsyncLocalStorage захватывает контекст в момент СОЗДАНИЯ асинхронного ресурса: таймера, сервера, сокета. Поэтому
всё, что обработчик создал, навсегда наследует { origin: эта подписка, depth } (MEASURED: в Node и в Bun 1.3.11
setTimeout и setImmediate видят контекст, critic-adv/bunprobe/als.mjs).
README.md:13 даже закрепляет это правилом: "NEVER change a key your subscription follows, neither in its handler
nor in anything the handler starts".
MEASURED (critic3-leak.ts, critic3-depth.ts, обычный процесс Node 26.11.0):
  - heartbeat. Модуль X следит за connection.[server, status] и на смену server вызывает команду владельца
    ensureConnected(). Владелец лениво запускает собственный heartbeat (setInterval), который пишет status. Первый
    же тик владельца объявлен эхом подписки X: "ui/connection changed status of connection, which it follows".
    Ошибка брошена в колбэке таймера, процесс завершён: "exit code 1". X ничего неправильного не сделал;
  - server. Модуль перезапускает HTTP-сервер при смене port (обычный паттерн "перезапуск по конфигу"), а
    admin-эндпоинт меняет port через команду владельца. Каждый запрос пользователя исполняется в утёкшем контексте
    обработчика. Итог: "70 admin requests; first failure at request 2 (failed: observation.delivery.echo);
    failures 69";
  - depth. Сервер перезапускается при смене config.listen, запросы пишут stats.hits, производный обработчик пишет
    config.listen из hits. Каждое независимое действие пользователя удлиняет утёкшую цепочку на 2 шага. После 32
    запросов производный обработчик получает observation.delivery.cascade: "cascade reports 8, first by
    config/derive; hits 40, derived listen 32". Производное состояние молча отстаёт: бомба замедленного действия,
    которая в тестах не видна.
VERIFIED: RATIONALE.txt:253-254 рассматривает только работу, начатую ДО подписки ("a timer created before the
subscription"), но не таймеры, созданные внутри обработчика.

Моё предложение, проверено прототипом (runtime-bounded/core.ts, около 15 строк): контекст считается только пока он
"открыт".
  - Контекст обработчика закрывается в конце его задачи доставки, включая её microtask checkpoint. Это setImmediate,
    поставленный вне контекста.
  - Контекст loader закрывается, когда run завершился.
  - Таймеры, серверы и соединения, созданные внутри, несут уже закрытый контекст, и их коммиты идут с глубины 0.
MEASURED на прототипе:
  - heartbeat: "exit code 0; reports: none";
  - server: "failures 0";
  - depth: "cascade reports 0; hits 40, derived listen 40";
  - C1, C2, C3, C4 и C10 по-прежнему ловятся на первом круге (1 доставка или 1 загрузка, 1 отчёт);
  - существующие наборы проходят: runtime-bounded/probes.test.ts a-keys pass 26, b-snapshot pass 27 (fail 0);
    runtime-b-bounded/probes.test.ts pass 26 (fail 0).
Цена прототипа: эхо, пересекающее задачу (команда, ждущая настоящий I/O; таймер), не ловится. Такой цикл ограничен
скоростью I/O, но бесконечен. Это известный пункт для ADR с владельцем.
Реализация: один общий "open"-флаг на задачу flush, а не setImmediate на каждый обработчик.
Тогда README.md:13 и :256-264 переписать так: "в обработчике и в том, что он делает в той же задаче (await без I/O,
microtask) и в теле loader пока идёт run".

M2 [P2, уверенность 7] Брошенное в асинхронном продолжении эхо завершает процесс
MEASURED (critic3-crash.ts, обычный Node): асинхронная команда без catch ("void requestLevel()") и queueMicrotask
дают "exit code 1; reports before exit: 1". Отчёт успевает уйти, но Host с сотнями модулей падает целиком из-за
ошибки одного модуля. С исправлением M1 сюда доходят только настоящие эхо.
README.md:13 ("Both are reported and thrown") об этом не предупреждает.
Решение для ADR:
  1) (Recommended) оставить "report and throw" как fail-fast, в README прямо написать, что необработанное
     асинхронное эхо завершает процесс Node, и что обработчик не запускает fire-and-forget async (асинхронная
     реакция идёт только через load);
  2) в асинхронных контекстах "report and refuse": не бросать, ничего не коммитить. Минус: set молча не
     выполняется, вызывающий получает старую ревизию.

M3 [P2, уверенность 8] Есть дешевле при том же нуле удержания
VERIFIED: @get-modular/resources (origin/main) packages/resources/src/features/scope/scope.ts: и #close, и #join
сначала вызывают #request(), а он синхронно прерывает signal, и только потом идут cleanup. Слушатель abort
отцепляет watch раньше, чем scope доберётся до записи `watch:<name>`. Значит, ни запись, ни child-scope на каждый
watch не нужны: долгов они не дают, удалить их рано нельзя (отсюда и было удержание N5).
MEASURED (runtime-signal/core.ts, тот же скрипт runtime-b/measure-watch-memory.ts):
  - только signal: "1064 bytes per live watch", удержание "22 bytes" (шум);
  - child-scope: 3080 и -92;
  - запись: 1282 и 511.
Наборы проходят: runtime-signal a-keys pass 26, b-snapshot pass 27; runtime-b-signal pass 26; critic-retention 0/50.
На пределах (64 на scope, 8192 на store) 3 КБ на watch приемлемы: 25 МБ на store в худшем случае. Но вариант
"только signal" в 2,9 раза дешевле, проще и равноценен. Черновик правила 5 CMS тогда говорит "привязана к
resources.signal вашего scope", а не "registers itself ... in its LIFO order".

M5 [P2, уверенность 7] Рецепт "Save on close" теряет данные при асинхронной записи
VERIFIED: README.md:211 "resources.use({ [Symbol.dispose]: () => { saved.write(store.read(["theme",
"density"]).values); } }, "prefs/save");". resources README (origin/main): "the result of a synchronous
`Symbol.dispose` is not awaited". Если write асинхронный (fs.promises), промис не ожидается, следующий cleanup
"prefs/file" закрывает файл во время записи, а отказ остаётся необработанным.
Исправление: `[Symbol.asyncDispose]: async () => { await saved.write(...); }`.
Именно в N4 речь шла о сохранности данных, поэтому рецепт должен быть безопасным.

3. Ответы на прямые вопросы
---------------------------
- Утекает ли контекст AsyncLocalStorage? Да: в таймер, созданный в обработчике, в сервер, перезапущенный в
  обработчике, и через команды в чужие модули. Даёт ложное эхо, падение процесса и накопление глубины (M1).
  Исправление с ограниченным сроком контекста проверено.
- Приемлемы ли 2,4x памяти? Да, по абсолютным цифрам. Но есть вариант дешевле при том же нуле: только signal,
  1064 байта на watch (M3).
- getBuiltinModule под бандлерами и в не-Node раннерах ведёт себя корректно: сборка не ломается, Bun работает.
  Риск в расхождении сред: в тестах без обнаружения, а в продакшене с броском (M6).
- Ловушка ли 5-секундный таймаут? Да, в двух видах: signal выключает защиту, а мок setImmediate обходит её (M4).
- Ошибки README: строка 13 (M1, M2), рецепт на 211 (M5), строки 136, 96 и 287-288 (M4, M6). Противоречий между README
  и api.d.ts по кодам, лимитам и владению я не нашёл.
