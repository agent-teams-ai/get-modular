1. Worktree: a fresh git worktree from `origin/main` in a directory of its own named `<repository>-<phase>`, on the
   branch the card names. Never reuse another agent's worktree, never touch other agents' processes.

   that version's `node` first on `PATH` (on 2026-10-15 all five repositories pin 26.11.1: agent-runtime
   since #232, `2fda5ffd7`, which keeps an explicit Node 24.21.0 compatibility lane, and agent-teams-ai/.github since
   `3094afe`). Before the first gate check that `node --version` equals the pin and `pnpm --version` matches the
   `packageManager` field. Never change the machine's default Node; if that version is not installed, install it
   beside the default or stop and report.
3. Gates: one at a time, in the foreground, never two heavy gates in parallel in one worktree. Never skip, weaken or
   bypass a gate; a failure caused outside the PR is reported, not
   worked around. Per repository:
   - get-modular: `pnpm check:changed` while editing, `pnpm check:fast` before review, `pnpm check` after the final
     commit (its integration tests clone HEAD and the custody check compares with the index, so commit first).
   - modularity-host-test: `pnpm typecheck`, `pnpm test`, `pnpm evidence` (after P6 also `pnpm lint` and `pnpm layout`).
   - agent-runtime: `pnpm check:changed` while editing, `pnpm check:fast` before review, `pnpm check` before opening and
     before merging the PR.
   - agent-teams-ai/.github: `node tools/feature-module-standard/check.mjs`,
     `node --test tools/feature-module-standard/check.test.mjs`, then `pnpm check` with full Git history.
   - engineering-foundation: `pnpm check:changed`, `pnpm check:fast`, `pnpm security:workflows` and focused tests
     before the PR; before merging, the complete CI matrix on the final head through `pnpm ci:full -- --pr <N> --wait`
     (engineering-foundation `AGENTS.md`, `docs/development/quality-gates.md`).
4. Git: author and committer from the repository's local `git config user.name` and `user.email`
   (the owner's identity in all five repositories); check `git var GIT_AUTHOR_IDENT` and
   `git var GIT_COMMITTER_IDENT` before committing; never override identity with `-c` or flags. Conventional commit
   messages without trailers (no co-author or generated-by lines) and without tool attribution, in commits, PR
   texts, comments and code. No `--no-verify`. No destructive git (`checkout --`, `restore`, `reset --hard`, `clean -f`,

7. Durable results: findings, measurements and evidence go to the PR and to the files the phase names, never only to a

## Goal: features as LEGO bricks (owner decision 5)

- A feature is a brick. It owns its contracts, use cases, domain rules, adapters and composition files. It connects to
  other features only through contracts: port types plus Get Modular descriptors. Its modules form one group; the root
  lists groups.
- A brick is testable alone: every module has an `isolate` test with its contract owners' fakes, use cases have unit
  tests with plain fakes, and no test needs another feature's implementation.
- A brick is replaceable: every contract with two implementations has the owner's contract suite; a replacement passes
  the suite and changes one group line and one oracle pin, nothing in the consuming features.
- Bricks nest (decision B): a feature may hold sub-features, sub-assemblies that move with it as one folder. A
  sub-feature is private to its parent; the parent's group includes the sub-feature groups, so the group tree mirrors
  the feature tree.
- Enforced by: the oxlint import-boundary and size rules (the Get Modular preset of `@get-modular/conformance` 0.3.0, or
  the P4 snippet if S0 0E rejects the preset; QN6), the Feature Module Standard checks (the EF-owned package of N3b in
  TEST; AR's FMS checker, which calls that package's kernel for the nested rules after N2), the Get Modular layout
  checks (`checkModuleLayout`: orphan modules, group tree, flat `composition/`, descriptor paths), `isolate`, contract
  suites, `smoke` and `checkWiring` per root, the shrink-only baseline for legacy code (EF, N3a), and the growth report
  (FMS metrics and EF budgets, warnings only).

## Owner decisions of 2026-10-11 (layout, declarations, scaling)

### Layout (decision 1)

A Get Modular module is a composition artifact (the Clean Architecture "main"), not a business boundary. The layout is
the same in every consumer and uses FMS v1 roles:

```text
src/features/<feature>/
  README.md                    feature card (decision 3a)
  contracts/                   port types other features use; plain TypeScript, no Get Modular
  domain/                      pure rules: deterministic, no I/O, no Get Modular
  application/
    use-cases/<verb-noun>.ts   one exported function (deps, input) => result
    ports/                     port types only this feature's use cases need
  adapters/
    inbound/                   transports into the feature
    outbound/                  DB, SDK, HTTP; classes with arrow-function fields allowed
  composition/                 flat; the only production place that imports @get-modular/*
    <feature>.contracts.ts     descriptors (defineContract) and the feature map
    <module>.declaration.ts    declareModule only
    <module>.module.ts         implement(...) wiring only
    <feature>.inputs.ts        input<C>() entries, only if the feature declares inputs
    <feature>.group.ts         group("<feature>", [...]); also lists the sub-feature groups
  features/                    sub-features, only if the feature has one (decision B)
    <sub-feature>/             the same layout, recursively, at any depth
src/composition/               Host-level files and the roots (<root>.root.ts)
<test-root>/features/<feature>/
  *.test.ts                    use-case, domain, isolate and contract-suite tests
  testing.ts                   the contract owner's fakes, suites and fake modules
  <feature>.wiring.ts          the feature's oracle part
  features/<sub-feature>/      the sub-feature's tests, mirroring the source tree
<test-root>/module/            root tests: smoke, checkWiring, checkNamespaces
```

- Only directories that hold real files (FMS "A directory MUST exist only when it contains a real owned artifact").
- The root's `modules` lists top-level feature groups plus its own root entries (named in `roots`), nothing else; a
  sub-feature's group is listed only by its parent's group.
- Layer direction (R2-5): `application/` and `domain/` never import `contracts/`, not even their own feature's. Use
  cases type their dependencies only with `application/ports/`; the module file in `composition/` maps the contract
  port types to them. FMS v1 :242-243 ("Domain and application code MUST NOT import public transport contracts") and
  AR's `LAYER_ALLOWED` (`feature-module-analysis.mjs:34-39`: application -> domain, application) already require it;
  TEST checks it through the FMS package (N3b).
- Descriptors live in `composition/<feature>.contracts.ts`, port types in `contracts/` or `application/ports/`. This
  refines the owner's wording ("contracts" directory) for three reasons: CMS :85-87 "Keep declarations, profiles and
  handle mapping in the outer composition adapter. Domain and application code must not import Core, Assembly ...";
  the AR FMS checker rejects any external import in `contracts`, `domain` and `application`
  (`scripts/architecture/feature-module-analysis.mjs:43` `EXTERNAL_IMPORT_ALLOWED`, `:308-314` `FM_EXTERNAL_IMPORT`), so
  `defineContract` cannot sit in `contracts/` there; and one rule then holds everywhere: `@get-modular/*` only in
  `composition/` and tests. Decided (Q1, owner, 2026-10-11).
- Tests go where FMS maps test roles: feature contract, adapter and conformance tests "SHOULD live under the module test
  root for that feature"; module-level tests under a module-level area. Both consumers put every feature test, focused
  unit tests included, under `<test-root>/features/<feature>/`, as AR does today (no test under `packages/*/src` on
  `f343f5cf`). This departs from the FMS SHOULD "Focused white-box unit tests SHOULD be colocated" so that production
  roots and builds never contain test code. AR's checker accepts both placements (`feature-module-tests.mjs`
  `declaredTestOwner`) and AR uses the test root; P7b records the choice in its adoption document, TEST in its README.
  Oracle parts and fakes are test code (F10). Decided (Q5, owner, 2026-10-11). A sub-feature's tests mirror its source
  path: `tests/features/<feature>/features/<sub-feature>/`.
- Nesting (owner decision B, replaces "features are siblings, never nest"): a feature may hold sub-features at
  `features/<parent>/features/<child>/`, to any depth, each with the same role layout. Rules, normative text and track
  in "Nested features" below. FMS v1 defines no sub-features and AR's v1 checker rejects them (it requires every feature
  root to be exactly `<production root>/features/<id>`, `scripts/architecture/feature-module-profile.mjs:204-205`, and
  reads the first path segment under a feature as its layer, `feature-module-analysis.mjs:77`). So TEST nests in P6,
  and AR nests only after N2; the AR block mapping says so until then.
- `composition/` is flat in every feature at every depth: AR ADR-0022:51 rejects nested paths under Host
  `src/composition/`, and flat files make the cross-feature import rules expressible as path patterns. No directory
  named `module` or `modules` anywhere in a feature (AR `SHARED_NAMES`, `feature-module-analysis.mjs:41`);
  `checkout.module.ts` is a file name, not a segment, and passes. `features` is not in `SHARED_NAMES`.

### Feature design and scaling (decision 3)

(a) Feature card, a body section of the feature `README.md`, filled when the feature is created and updated with every
module added. AR keeps its README front matter unchanged (`feature-module-readme.mjs` parses it); the card is body text.

```markdown
## Feature card

- Purpose: <one sentence: the capability this feature owns>
- Parent: <parent feature, or "none" for a top-level feature>
- Publishes: <capability id rN> - <who consumes it>, one per line; republished sub-feature contracts marked (republished)
- Consumes: <capability id rN> from <feature>, one per line
- Modules: <implementation id> - <one line>; planned ones marked (planned)
- Sub-features: <sub-feature> - <one line>, one per line, or "none"
- Expected growth: <what the next releases add here>
- Likely split seams: <parts that could become sub-features or sibling features, and the contract between them>
- Split signals now: <modules>/12 modules, <use cases>/20 use cases, depth <n>/3, aggregates: <names>
```

(b) Split signals, in the guide; the numbers are consumer policy and the owner may tune them: about 12 modules in
`composition/`; about 20 use cases; two aggregates with independent invariants or lifecycles; parts that change for
different reasons. Two recipes (guide section 8), chosen by the nature of the part:

- "Extract a sub-feature" when the part is tightly bound to the feature: it uses the feature's contracts or shares its
  aggregate or lifecycle, and no feature outside the parent uses it directly. It moves to
  `features/<feature>/features/<part>/`; the parent's group replaces the moved module lines with one sub-feature group
  line; the root does not change.
- "Split into sibling features" when the parts are independent: other features use the part directly, or it changes
  for its own reasons and needs nothing of the feature's internals. It moves to a sibling directory at the same level;
  the root (or, for a sub-feature, its parent's group) gains one group line.

Both recipes keep every capability id, implementation id and revision (CMS identity rule 5), so `checkWiring` passes
with the same pins and consumers are unaffected because they depend on contracts. Past depth 3 the growth report warns
(owner decision B); the guide then prefers a sibling.

(c) Warning-only growth report; it never fails CI.

### Nested features (decision B)

Owner decision of 2026-10-11, binding: features nest to any depth. It replaces "features are siblings, never nest". The
owner's reasoning: a package is a unit of reuse and distribution, a feature is a unit of meaning and ownership; a big
feature with its sub-features moves together as one folder, like a LEGO sub-assembly; DDD subdomains. The old sibling
rule was written hastily and is not dogma; changing FMS and the checkers is acceptable. Depth is the engineer's choice
with no policy limit; the growth report warns past depth 3. Mechanical ceilings, not policy: Get Modular groups nest at
most 16 levels with `modules` as level 0 (ADR-0036 limit, API rule 3), so a feature at depth d is group level d and a
tree deeper than 16 cannot be assembled; AR's checker walks at most 128 path levels (`feature-module-limits.mjs`).

Rules. FMS wording in `fms-nested-features-draft.md` (section Sub-features); Get Modular wording in P4.

1. Path and layout. A sub-feature lives at `features/<parent>/features/<child>/`, and every feature at any depth uses
   the same role layout with a flat `composition/`. Why this shape: one container name at every level makes the layout
   self-similar, so a feature folder moves between levels unchanged; feature names never collide with role names
   (`features/<a>/<b>/` makes a child named `domain` or `contracts` ambiguous and breaks every checker that reads the
   first segment below a feature root as its role, AR `feature-module-analysis.mjs:77`); a checker resolves any path
   with one rule (the first segment below a feature root is a role, `features`, or a mapped file such as `README.md`)
   and gives each file to the deepest feature root that contains it; `features` is neither an FMS role nor an AR shared
   name (`SHARED_NAMES`, :41); test paths mirror it. Rejected: `features/<a>/<b>/` (collisions above) and a second
   container name such as `sub-features/` (moving a feature between the top level and a parent would rename its
   container).
2. Private by default. A top-level feature is visible to the whole production module; a sub-feature only to its parent
   and the parent's descendants (lexical scoping). Other features, the roots and other modules reach a sub-feature only
   through contracts its parent republishes. Republication is a pure re-export of a direct child's public surface from
   the parent's public surface (Get Modular layout: `export { Store } from
   '../features/storage/composition/storage.contracts.ts'` in the parent's descriptor file, port types likewise in
   `contracts/`), one level at a time, never from a grandchild, and declared in the FMS profile where one exists (in
   TEST: in the layout checks' configuration).
3. Dependencies cross feature boundaries only through public contracts of visible features (in FMS v1.1 terms the
   public entrypoint and, from composition only, the composition contract, which in the Get Modular layout is
   `composition/<feature>.contracts.ts`):
   - upward: a feature may use the public contracts of its parent and every ancestor;
   - downward: a parent may use the public contracts of its direct sub-features, never of a grandchild;
   - lateral: siblings, and siblings of ancestors, through public contracts; never internals;
   - assembly: a parent's `composition/<parent>.group.ts` lists its direct sub-features' groups; nothing else wires a
     sub-feature;
   - no cycles (QN2, decided by the owner 2026-10-11): the graph of downward and lateral use edges is acyclic, counting
     runtime and type-only references alike (AR's checker already reports `FM_TYPE_CYCLE`,
     `feature-module-edges.mjs:25-26`). Upward use edges (a sub-feature using an ancestor's contracts), assembly edges
     and republications are outside that graph, because an ancestor's public contracts are the shared language of its
     subtree and a parent moves with its sub-features; every cycle this admits closes on an ancestor and stays inside
     its subtree, since code outside a subtree can reach only its root feature. No load-time import cycle may exist
     between files of different features (type-only imports do not count for this file-level rule). In the Get Modular
     layout a parent's map extends its sub-feature's map through `import type` (a downward type-only edge) and the
     sub-feature's declarations import the parent's descriptor values (upward), so descriptor files never import each
     other at load time. The stricter variants (a strict graph over every use edge; a parent that never uses its
     sub-features) were not chosen. The critic's R2-8 cases are fixtures (FMS draft examples; N3b `./fixtures`);
   - `domain/` and `application/` import no other feature and no `contracts/`, their own included; they type `deps`
     with their own `application/ports/` (R2-5; guide 5 and 7).
   TEST example (P6): `sessions` uses `Store` and `Cache` of its sub-feature `storage` (downward); `storage` uses
   `Journal` and `SessionId` of `sessions` (upward); accepted. The top-level `counter` cannot import `storage`.
4. The group tree mirrors the feature tree: `group('sessions', [session, storage])`, `group('storage', [cache, store])`,
   root `modules: [counter, sessions]`. A group's name is its feature's own segment, so `groupPath` reads like the
   feature path (`['sessions', 'storage']`). Identities are hierarchical when created (`<product>/<parent>/<child>/
   <module>`, for example `test/sessions/storage/<name>`) and immutable afterwards: CMS identity rule 5 ("IDs are
   immutable and never reused") and rule 4 (a namespace names a semantic owner, "not a team, repository, package or
   directory"). A moved feature keeps its ids, so an id records where its owner was created and may differ from the
   current path. Decided (QN1, owner, 2026-10-11). The CMS (P4) adds: "Id segments are a namespace at creation time,
   not a path. The FMS identity of a feature (its path) and a Get Modular id are different concepts;
   `checkNamespaces` never compares ids with paths."
5. Moving a feature moves its folder with every sub-feature. Inside one production module this is no extraction and
   needs no extraction decision. Consumers that depend on contracts change only import paths, or switch to the
   parent's republication when the move hides the feature from them; `checkWiring` passes with unchanged pins; an FMS
   profile changes in the same PR where one exists.
6. Two split recipes, "extract a sub-feature" and "split into sibling features", chosen by the growth signals and the
   nature of the part (decision 3b, guide section 8).
7. The consumer `AGENTS.md` block keeps nine rules; rules 1, 2 (R2-5), 6, 7 and 8 change, and both repository
   mappings change (TEST admits sub-features in P6; AR carries the NOW subset from P7-now and states that it does not
   nest until N2).

## API of the train

Implementers build this; names may change only through the ADR-0036 review.

```ts
// @get-modular/assembly 0.5.0: new and changed
export type ContextAdapter<X> = <Deps, R>(name: string, factory: (dependencies: Deps, context: X) => R) =>
  (dependencies: Deps, context: FactoryContext) => R;    // `scoped` from resources satisfies it; the only admitted one
export declare function implement<C>(): {
  <const D extends ModuleDeclaration, I>(declaration: D & ValidDeclaration<C, NoInfer<D>>,
    factory: ModuleFactory<C, NoInfer<D>, I, FactoryContext>): ModuleEntry<C, D, I>;
  <const D extends ModuleDeclaration, I, X>(declaration: D & ValidDeclaration<C, NoInfer<D>>,
    factory: ModuleFactory<C, NoInfer<D>, I, X>, adapter: ContextAdapter<X>): ModuleEntry<C, D, I>;
};
export declare function input<C>(): <const D extends ModuleDeclaration & { readonly slots: readonly [] }>(
  declaration: D & ValidDeclaration<C, NoInfer<D>>) => InputEntry<C, D>;
export declare function group<const M extends readonly (AnyEntry | ModuleGroup)[]>(name: string, members: M):
  ModuleGroup<EntriesOf<M[number]>>;
export declare function entriesOf(modules: readonly (AnyEntry | ModuleGroup)[]): readonly AnyEntry[];
export type Assembly<C> = {                                       // bindFactory and bindInput are removed
  readonly prepare: (input: { modules; roots; inputs? } & ({ profileId; bindings? } | { composition })) =>
    Promise<AssemblyPreparationResult<R, N>>;                     // tuple `modules` in the profileId form only
};
```

Runtime shapes and rules:

1. An entry is a frozen null-prototype `{ declaration, factory }`: `declaration` is Assembly's frozen snapshot,
   `factory` the function after the adapter. An input entry is `{ declaration }`. A group is a frozen
   `{ name, members }` with a frozen copy of `members`. A private WeakSet authenticates each kind; copying fields forges
   nothing (the guarantee handles have today). The fields are public inert data so `smoke` can rebuild a tree with
   `implement` and `group` alone; Assembly gets no hook.
2. `implement` snapshots and validates synchronously and calls `adapter(declaration.implementationId, factory)` once.
   It throws `AssemblyBindingError` with the existing codes `assembly.bind.invalid-declaration`, `limit` and
   `invalid-factory` (an adapter that is not a function or returns no function is `invalid-factory`). `declareModule`
   and `defineContract` already throw `AssemblyBindingError` at import (`contract.ts:12-14`), the CMS snapshot-at-bind
   rule (:698-702) stays intact, and no new preparation code is needed for it.
3. `group` validates synchronously and reads own data properties only, so no getter runs: name non-empty, at most 128
   UTF-8 bytes; `members` dense, at most 4096, authenticated entries or groups, no input entries; subtree depth at most
   16 with `modules` as level 0, so a 17th level throws `assembly.bind.invalid-group` at creation (new code). At type
   level `members`, and `modules` in the `profileId` form, must be tuples (`number extends M["length"]` is rejected, as
   `ValidDeclaration` does for declarations), so an annotated `AnyModuleEntry<C>[]` fails to compile instead of losing
   the map check. The `composition` form accepts `readonly AnyModuleEntry<C>[]`: a Host that compiles its own profile
   (CMS :718-719, ADR-0035:46-47), such as a later plugin Host, builds its list at run time; the per-entry map check is
   lost there, as for arrays today, and Core checks the plan (F8). ASSUMPTION: S0 shows the tuple rule costs at most 1%
   on the budget fixture.
4. `prepare` flattens `modules` depth-first, counting group nodes and entries against the existing 4096 ceiling
   (`assembly.prepare.limit`), and then works as ADR-0035; order and nesting never change the profile, the plan or the
   digest. Duplicates (an entry reached twice, or two entries with one implementation id, input entries included) fail
   with new `assembly.prepare.duplicate-module`,
   `cause: readonly { implementationId, paths: readonly (readonly string[])[] }[]`, every occurrence listed; no
   deduplication. A forged group or entry, an input entry in `modules` and a root outside `modules` keep the existing
   codes `assembly.prepare.handles`, `input-handles` and `roots` (F12). A root is an entry reached through `modules`;
   an input entry appears only in `inputs`. Existing codes keep their names: codes are identifiers, and renaming would
   only churn consumer maps.
5. `UnresolvedBinding` gains `groupPath: readonly string[]` (group names from `modules` down to the consumer, `[]` at
   top level).
6. Removed from the public API: `bindFactory`, `bindInput`, `FactoryHandle`, `AnyFactoryHandle`, `InputHandle`,
   `AnyInputHandle`, `RootHandles`, `InputHandles`. New: `ModuleEntry`, `AnyModuleEntry`, `InputEntry`,
   `AnyInputEntry`, `RootEntries`, `InputEntries`, `ModuleGroup`, `ContextAdapter`. Kept: `assemblyFor`,
   `declareModule`, `defineContract`, `ModuleFactory`, `FactoryDependencies`, `AssemblyBindingError`, the explicit
   `prepare({ composition })` path. No `isModuleEntry` (F5).
7. Entries are created at the top level of `<module>.module.ts` by default. A factory that closes over Host-level values
   (AR passes adapter factories and Host callbacks) gets its entry from a composition-adapter function; the list a root
   passes to `prepare` never depends on run-time values (CMS rule 5 as it reads today).
8. `ContextAdapter<X>` is the type `scoped` from `@get-modular/resources` satisfies; `scoped` is the only admitted
   adapter. An adapter that reads `scope` or adds anything but `resources` recreates the opaque context ADR-0031 rejects
   (GM-REQ-012) (F7).

Conformance 0.3.0:

- `smoke` keeps its signature. Its api's `prepare` first calls the real `prepare` with the input as given and returns any
  failure unchanged; only then it rebuilds every entry with a wrapped factory
  (`implement()(entry.declaration, wrap(entry.factory))`), every group with `group(name, members)`, remaps `roots` by

### 0C Own-property port check

Feasible and cheap, about 40 LOC and one walk per created capability, with known limits. Rule to prototype:

- For each capability value of each constructed module that is an object (functions are skipped), walk the prototype
  chain until `Object.prototype` or `null`. Stop at a realm intrinsic container prototype captured at load (`Array`,
  `Map`, `Set`, `WeakMap`, `WeakSet`, `Date`, `RegExp`, `Promise`, `Error`, `ArrayBuffer`, `DataView`, typed arrays,
  and `globalThis.Buffer?.prototype`): those are data, not ports. Also stop at a prototype whose own prototype is `null`
  and that has an own `hasOwnProperty` (an `Object.prototype` of another realm: vm, test runners). On every other
  prototype, each own property except `constructor` that is a function-valued data property or an accessor is a
  violation. Read descriptors only, never invoke a getter; string and symbol keys. Proxy traps run during the walk:
  documented (F15).
- A class with arrow-function fields passes (its prototype holds only `constructor`). Classes with methods,
  `Object.create(proto)` with methods, and Node or SDK instances (EventEmitter, URL, AbortSignal, iterators, a database
  pool) fail and are wrapped in a port object.

  property), a method extracted unbound as a function-valued capability, nested objects, run inputs, own accessors on
  the capability object, and a `Map` capability (it passes; the registry ban stays a review rule). No oxlint rule covers
  `this` in object literals (`no-invalid-this` is missing; `object-shorthand` "never" also bans property shorthand).

Base draft of ADR-0036:

```markdown
# ADR-0036: Compose roots from module entries and static groups
## Context
After ADR-0035 each module is still bound in the root and listed again in `factories`; owning modules repeat their
id in `scoped(declaration.implementationId, factory)`, and a factory typed with `ModuleContext` bound without
`scoped` fails with TS2345 in the root, far from the module. ADR-0032 lets teams bind fragments under their own
maps, but the Consumer Module Standard requires binding through the `api` that `smoke` passes, so fragments cannot
reach a production root, and every module lands in one flat root.
## Decision
- `implement<C>()(declaration, factory, adapter?)` creates a module entry: a frozen pair of the declaration and its
  factory, typed by the map it was implemented under and invariant only in the capabilities the declaration uses, as
  handles were. `adapter` turns a factory written for another context into one for `FactoryContext`; Assembly calls
  `adapter(declaration.implementationId, factory)` once. `scoped` from `@get-modular/resources` is such an adapter;
  Assembly does not import that package. `input<C>()(declaration)` creates an input entry.
- `group(name, members)` creates a frozen static list of entries and groups. `name` is a navigation label: it never
  enters the profile, the plan or the digest. Groups form a tree; an entry reached twice, or two entries with one
  implementation id, fail with `assembly.prepare.duplicate-module`, naming both group paths.
- `prepare({ profileId | composition, bindings?, modules, roots, inputs? })` replaces `factories`. Assembly flattens
  `modules`, binds each entry once and proceeds as in ADR-0035. Order and nesting do not affect the profile, the
  plan or the digest. A root is an entry reached through `modules`; an input entry appears only in `inputs`.
- `bindFactory`, `bindInput` and handle types leave the public API. `smoke` wraps every entry when the root calls
  `prepare`.
### Precedence
Supersedes the binding API of ADR-0032 and, in ADR-0035, the rejected alternatives "A separate `compose` method" and
"A `bindAll` helper": measured on the fragment fixture, entries in 20 groups cost 499,401 instantiations against
515,235 at 500 modules (tsc 7.0.2) and 709,744 against 711,318 (TS 5.8.3). The factory context stays closed
(ADR-0031); the scope name is the implementation id supplied when the adapter is applied, not a context field.
GM-REQ-002, -011 and -012 are unchanged: groups are inert static imports, nothing scans or discovers, and no factory
receives a resolver, a container or a registry. Core semantics, the wire format and the plan digest do not change.
## Consequences
- A module appears once in its feature's group; a root lists features.
- A factory that reads `resources` without the adapter fails in the module file.
- Feature maps compose by interface extension; TypeScript rejects two features that disagree on a contract.
- Breaking for roots, `isolate` calls and code naming handle types; a codemod rewrites the call shape.
## Rejected alternatives
Runtime discovery or glob imports (GM-REQ-011); decorators (GM-REQ-012); generated group files with a check mode
(one line per module saved for a generator, a build step and generated files); deduplicating a twice-reached entry
(features would pull other features in silently); keeping `bindFactory` beside entries (two ways to bind); feature
functions taking a narrowed `api` (double listing stays).
```

Base draft of ADR-0037:

```markdown
# ADR-0037: Pin providers, not completed rows, in the binding oracle
## Context
Under ADR-0035 a completed row is fixed by its slot's capability and the single bound provider, so writing it
restates the declaration. At hundreds of modules the row table grows by about two rows per module, changes with
every slot and is maintained by copying output, the main risk ADR-0035 names.
## Decision
- The independent oracle states wiring decisions: for each capability a selected module provides, the implementation
  or implementations providing it; the root implementations; and every row completion does not produce (`optional`,
  `many`, explicit rows) exactly as written.
- `checkWiring(composition, oracles)` in `@get-modular/conformance` compares the plan with the union of the oracles:
  selections equal the providers and roots; every completed row binds the pinned provider of its capability; every
  listed row equals its plan row; a conflict between oracle parts fails. It reports every difference.
- A feature may keep its own oracle part. The oracle is never derived from the profile, the plan or the
  implementation.
## Consequences
- Provider replacement, an added or removed module, a changed root and every explicit, optional or many row fail the
  oracle.
- Accepted weakening: a new `required` slot, or a slot moved to another capability, binds to the pinned provider
  without an oracle change; review it as a declaration change.
## Rejected alternatives
Full rows per feature (same size, changes with every slot); a golden file refreshed from output; cross-feature rows
only (misses replacement inside a feature).
```

and `billing`, and `orders` has the sub-feature `discounts` (`acme/orders/discounts/...`): `orders` `checkout` uses
`Discounts` (downward), `discounts` uses `OrderLines` from `orders` (upward), and `billing` uses `Discounts` through the
republication in `orders.contracts.ts`.

0. **How to use this guide; rules at a glance** (old sections 0 and 2 merged, F17). Audience: agents and people writing
   or reviewing features and modules. The CMS holds the normative rules, this guide the how-to; pin both at the same
   commit; where they differ the CMS wins and the guide has a bug. A table "I want to ..." -> section, and the nine rules
   of the consumer block, each linked to its CMS anchor and guide section. No code.
1. **The model: features as LEGO bricks.** The goal in five lines (independent bricks, contracts only, alone-testable,
   replaceable, the root assembles groups). The artifacts and their owners: port type, descriptor and feature map,
   declaration, module entry, feature group, input, root, oracle part, fake and suite. The decision-1 tree with FMS
   roles and the sub-feature container at any depth; a table of what each file may import, which features it may see
   (its sub-features, its ancestors, the siblings of itself and of its ancestors) and which check enforces it (oxlint
   rules, the FMS package or the consumer's FMS checker, the Get Modular layout checks, review), and how a consumer
   wires those shared checks. Examples: the project tree with
   `orders/features/discounts`; the root (about 10 lines).
2. **Designing a feature.** Feature, module and use case (FMS: a feature is a cohesive capability, never one per class
   or endpoint; a module is a composition seam, CMS "not a graph node merely because it is new"; a use case is one
   operation); which contracts to publish and which ports to own; identities by link to the CMS; top-level feature or
   sub-feature (a package is a unit of reuse and distribution, a feature at any depth a unit of meaning and ownership;
   nest a tightly bound part, keep independent parts siblings); the feature card, filled at creation and updated with
   each module; the first module. Examples: the card template and filled cards for `orders` and `discounts`.
3. **Add a new module.** Steps: identities; port type; use-case file and domain rules; `<module>.declaration.ts`;
   `<module>.module.ts`; `isolate` test; one group line; one oracle line; run typecheck, lint, the layout checks,
   `smoke`, `checkWiring`, `checkNamespaces`. Ends with a checklist. Examples: `orders` `checkout`:
   `checkout.declaration.ts`, `checkout.module.ts` (about 25 lines), `application/use-cases/apply-discount.ts`,
   `domain/discount-rules.ts`, `tests/features/orders/checkout.test.ts`; the diffs of `orders.group.ts` and
   `orders.wiring.ts`.
4. **Declarations.** What a declaration file may import and why (inert, no side effects, ADR-0029; the allow-list);
   one provide and several provides (one oracle pin each); two implementations of one contract (one `moduleId`, distinct
   `implementationId`s, chosen by a `bindings` row or by separate roots, both pass the suite); inputs
   (`<input>.declaration.ts` without slots, `<feature>.inputs.ts`); variants from one spec may share a file; a later
   plugin manifest is generated from these files. Examples: a two-provides declaration; postgres and memory
   implementations with the root `bindings` row and oracle rows; an input declaration and entry.
5. **Cross-feature slots.** Only through contracts: the declaration imports the other feature's
   `<feature>.contracts.ts`; the feature map extends that descriptor; the use case types `deps` with its own port in
   `application/ports/`, which the other feature's port satisfies structurally, so application code never imports
   another feature; never import its modules, groups, use cases or adapters; the root lists both groups; disagreeing
   maps fail with TS2320; no feature cycles (FMS), and Core rejects cyclic modules. A declaration imports only
   composition contracts; domain and application code never do. Where a consumer's FMS checker forbids importing
   another feature's `composition/` (AR until N2 adds the declared composition entrypoint), the descriptor is
   Host-level. Sub-features: only visible
   features (own sub-features downward, ancestors upward, siblings of itself and of its ancestors laterally) with the
   descriptor paths for each (`../features/<child>/composition/`, `../../../composition/`, `../../<sibling>/composition/`);
   a sub-feature is private, so code outside its parent uses the parent's republication (`export { Discounts } from
   '../features/discounts/composition/discounts.contracts.ts'`), one level at a time; downward and lateral edges must
   stay acyclic, type-only references included, an upward use never counts, and no load-time import cycle may cross
   features; a parent's map extends
   its sub-features' maps through `import type`. Examples: `orders` `checkout` with slot `payments` from `billing`;
   `orders` and `discounts` using each other (downward and upward); `billing` using `Discounts` through the
   republication.
6. **Ports as factory functions.** Why this is the official form: no `this`, members survive destructuring, closures
   hold state, the own-property check passes, function-typed properties are checked contravariantly. How
   `<module>.module.ts` builds the port from use cases (`{ apply: (input) => applyDiscount(deps, input) }`); a member may
   stay inline only as a one-expression forward without a branch. Examples: the port object; a class with prototype
   methods as the contrast (`text`).
7. **Use cases and pure logic.** Signature `(deps, input) => result`; `deps` is a narrow record of port types and the
   module's own resources, never the whole dependency record or a Get Modular type; a use case imports only its own
   `application/ports/` types, other files of its own `application/` and its own `domain/` (F16), never `contracts/`,
   not even its own feature's (FMS v1: "Domain and application code MUST NOT import public transport contracts"); the
   module file maps contract port types to the use case's ports (R2-5); one exported function per file, named
   `<verb-noun>`; domain rules
   deterministic, with time, ids and randomness passed in (FMS Domain); nothing in `application/` or `domain/` imports
   Get Modular. Examples: `apply-discount.ts` with `ApplyDiscountDeps`; `discount-rules.ts`; their unit tests with plain
   object fakes.
8. **When and how to split** (old section 6 merged with the owner's split section). Inside a module first: more
   use-case files; a port of more than about 7 members or members that change for different reasons split into modules
   only at a real composition seam (separately replaceable capability, own resources or lifecycle). Then the feature:
   the split signals (about 12 modules in `composition/`, about 20 use cases, two aggregates with independent invariants
   or lifecycles, parts that change for different reasons, depth over 3; numbers are consumer policy) and the growth
   report. Choose the recipe by the part, not by size: tightly bound (it uses the feature's contracts or shares its
   aggregate or lifecycle, and nobody outside the feature uses it directly) -> recipe A; independent (other features use
   it directly, or it changes for its own reasons and needs nothing internal) -> recipe B; past depth 3 prefer B.
   Recipe A, "extract a sub-feature": (1) write the seam into the card; (2) create `features/<feature>/features/<part>/`
   with its README card (`Parent: <feature>`); (3) move the part's port types to `<part>/contracts/` and descriptors to
   `<part>/composition/<part>.contracts.ts`, keeping every capability id and revision (ids name the semantic owner, not
   the directory); (4) move the declaration, module, use-case, domain and adapter files, ids unchanged, and the tests to
   the mirrored test path; (5) create `<part>.group.ts` and replace the moved lines in `<feature>.group.ts` with one
   `<part>` line, the root unchanged; (6) the parent's map extends `<part>`'s map through `import type`; (7) move the
   oracle pins to `<part>.wiring.ts` and add the part to the root test; (8) code outside the feature that used a moved
   contract imports the feature's republication, which the feature adds to `<feature>.contracts.ts`; (9) declare the
   sub-feature, its edges and any republication in the consumer's FMS profile (AR after N2: profile, edges, decision;
   TEST: the layout checks' configuration).
   Recipe B, "split into sibling features": (1) write the seam into the card; (2) create a sibling `<new>/` next to the
   feature (under `features/` at the top level, or in the parent's `features/` for a sub-feature) with its README card;
   (3) move the contracts whose owner changes, port types to `<new>/contracts/` and descriptors to
   `<new>/composition/<new>.contracts.ts`, ids and revisions unchanged; (4) move the declaration, module, use-case,
   domain, adapter and test files, ids unchanged; (5) create `<new>.group.ts` and remove those lines from the old group;
   (6) add one line to the root's `modules` (or to the parent's group for a sub-feature sibling) and one `extends` to the
   root map; (7) move the oracle pins to `<new>.wiring.ts` and add the part to the root test; (8) where the old feature
   still uses a moved capability, its declaration imports the new descriptor file (section 5), never the moved modules;
   (9) register the new feature and its edge in the consumer's FMS profile (AR: profile, edge, decision). In both
   recipes features outside change nothing but import paths because they depend on contracts; the plan's selections and
   rows stay the same, so `checkWiring` passes with the same pins. Examples: `orders` extracting `discounts` (A);
   `orders` split into `orders` and `payment-intents` (B); trees before and after.
9. **Resources.** When a module owns something to release; `implement(..., scoped)`; `resources.setup` vs `use`; names;
   never close a borrowed dependency; child scopes; subscriptions and running work; what TS2339 "Property 'resources'
   does not exist on type 'FactoryContext'" means (the adapter is missing); link to the CMS module author rules 1-13.
   Example: a module that opens a queue with `resources.setup` and registers a subscription disposer.
10. **A stateful adapter as a class.** When a class is allowed (state with identity, an SDK or client wrapper, a test
    fake that tests inspect); it lives in `adapters/outbound/`; arrow-function fields, `#private` state, private
    constructor and `static async create`; never pass the instance as the port, build a port object with only the port
    members so `close` stays with the owner; wrapping a legacy class adapter or a third-party client. Example:
    `PgOrders` with `static async create`, created inside `resources.setup`, and the port built from its fields.
11. **Fakes and contract suites.** The contract owner keeps one fake, one suite and a fake module in its feature test
    root's `testing.ts`, which production never imports; fakes are factory functions, or classes with arrow fields when
    tests inspect state; typed by the port, no `any` or casts; `runContractSuite` against the fake and every
    implementation once two exist; replacing an implementation means passing the suite and changing one group line and
    one pin. Examples: `createPaymentsFake()`, `contractSuite(Payments, {...})`, the runner line with
    `(name, body) => t.test(name, body)`.
12. **Optional, many and several providers: explicit bindings.** Completion fills only `required` slots with exactly
    one candidate; `optional` needs a row (`[]` or one provider); `many` an ordered row; two providers of one capability
    need a row for every consumer; rows live in the root's `prepare({ bindings })` and the same rows in the oracle
    part's `rows`; group-level bindings do not exist. Example: a root with a `many` row and an `optional` row, and the
    matching oracle rows.
13. **Groups and the root.** One line per module in `<feature>.group.ts`, sorted, one member per line; never in the
    root or behind a condition; a parent's group also lists its direct sub-features' groups, so the group tree mirrors
    the feature tree and `groupPath` reads like the feature path; a new top-level feature adds one line to the root
    `modules`, one `extends` to the root map and one oracle part, a new sub-feature one line to its parent's group;
    resolving a merge conflict (keep both lines; the union attribute if adopted); the layout checks catch a module
    missing from its group and a sub-feature group outside its parent's group (decision 3c). If 0B selects
    codegen, this section describes the generator instead. Examples: the group diff; the root diff for a new feature;
    `orders.group.ts` listing `discounts`.
14. **Host values, inputs and variants.** Per-run data and parent ports are inputs (`input<C>()`, `run({ inputs })`);
    Host-level singletons and adapters may be captured by factories created in a composition-adapter function whose
    list never depends on them; a variant is a separate root with its own `profileId`, `smoke` and oracle; no `if` in a
    module list. Examples: an input declaration, entry and run; a `createOrdinaryGroup(adapters)` shape; two roots.
15. **Reading errors.** `unresolved-binding` (fields including `groupPath`; fix table by cardinality and candidate
    count: zero candidates -> add the providing feature to the root or write the provider; several -> keep one or add
    rows; optional or many -> add the row); `duplicate-module` (every path); `assembly.bind.*` thrown at import;
    `assembly.prepare.roots`; `core-rejected` on a revision mismatch; type errors (TS2339, TS2320, "capabilities missing
    from the preparing map", an annotated list rejected); `conformance.ports.prototype-member`,
    `conformance.wiring.mismatch`, `conformance.layout.violation`; lint and layout-check messages;
    `describeWiring` to see the plan. Examples: a printed `unresolved-binding` cause with its fix; a `describeWiring`
    excerpt.
16. **Change a contract in place; upgrades with codemods.** Raise `revision` on every value-type change and update
    provider, consumers, fake and suite in one change; Core rejects a mismatch; never `/v2` ids; for a Get Modular
    upgrade run the codemod on a clean tree, then the "By hand" list of the changeset; what `0.4-0.5` does and does not
    do (the layout move is by hand). Examples: a revision bump diff; the codemod command and a `--dry` listing.
17. **Tests.** Use-case and domain unit tests (plain fakes, no Get Modular); `isolate` per module with `await using`; a
    suite per contract; per root `smoke`, `checkWiring` over the feature parts, `checkNamespaces`; what each proves
    (`smoke` proves cleanup, not wiring; the oracle states wiring decisions); a feature's tests import only its own code,
    the public surfaces and `testing.ts` of features it may see, and Get Modular; a sub-feature's tests live at the
    mirrored path (`tests/features/orders/features/discounts/`); no sleeps; close every scope. Examples:
    `checkout.test.ts`, `orders.wiring.ts`, `discounts.wiring.ts`, a root test with all root checks.
18. **Identities, namespaces and plugins.** Links only (F17): the CMS identity and namespace rules
    (`<product>/<context>/<name>`, `<product>/<feature>/<sub-feature>/<name>` for a module created in a sub-feature;
    ids never change when files or features move; id segments are a namespace at creation time, not a path, and
    `checkNamespaces` never compares ids with paths, QN1); ADR-0029 and section 4 for plugin readiness; the plugin
    manifest
    follow-up. No code.
19. **Anti-patterns**, a table of pattern, reason, instead (F17, about 12 rows):
    reaching into another feature's sub-feature, or listing a sub-feature's group in the root (breaks private by
    default; the parent can no longer restructure its subtree; use the parent's republication);
    a sub-feature per class, per endpoint or only to isolate a folder (FMS; ceremonial depth);
    decorators (class-only, registration by import side effect, the class type does not change so the map loses typing;
    GM-REQ-012);
    runtime discovery, glob or dynamic imports of modules in production code (nondeterministic, bypasses admission and
    review; GM-REQ-011);
    prototype methods or `this` in ports (`this` is lost on destructuring; the check fails on prototype methods and
    cannot see object-literal `this`);
    method signatures or inferred types (`ReturnType<...>`) in port types (bivariant parameter checks accept breaking
    changes; lint cannot see an inferred type);
    logic in `*.module.ts` or anything but the declaration in `*.declaration.ts` (untestable without Get Modular;
    declarations must stay inert);
    conditional module lists or variants by flag (wiring depends on run time; `smoke` and the oracle cover one shape);
    annotated module lists (lose the map check; rejected in the `profileId` form);
    importing another feature's modules, groups, use cases or adapters (hidden coupling, `duplicate-module`, the feature
    stops being a brick);
    registries, `get(key)` inputs, service bags, per-instance data captured in closures (a service locator; instances
    leak into each other, ADR-0031);
    copying `describeWiring` or a plan into the oracle (the oracle then proves nothing);
    `any`, double casts or `as never` in wiring or fakes (false type claims).
    Examples: short `text` snippets for the first four.
20. **Checklists.** "New feature" (top-level or sub-feature first), "new module" and "review a feature or module
    change" (visibility, cycles, republication, group tree) checklists, about ten lines each. No code.

```markdown
## Get Modular modules

When you add or change a feature, a Get Modular module or a composition root, read the module authoring
guide (https://github.com/agent-teams-ai/get-modular/blob/<pinned commit>/docs/guides/module-authoring.md)
and the Consumer Module Standard it links. Features are independent bricks: they connect only through
contracts, each one is tested alone with its contract owners' fakes, and the root assembles feature groups.
Always:

1. Lay out each feature as `features/<feature>/{contracts, domain, application/{use-cases, ports},
   adapters/{inbound, outbound}, composition}` and create only the directories that hold real files.
   Where the mapping below admits it, a feature may hold sub-features in its own
   `features/<sub-feature>/`, each with the same layout, to any depth: nest a tightly bound part so it
   moves with its parent as one folder, and keep independent parts as siblings. A sub-feature is
   private: code outside its parent reaches it only through contracts the parent republishes.
2. A use case is `application/use-cases/<verb-noun>.ts` exporting one function `(deps, input) => result`,
   where `deps` is a narrow record of port types from `application/ports/`. `application/` and `domain/`
   never import `contracts/`, not even their own; the module file maps between them. Pure rules go in
   `domain/`; DB, SDK and HTTP code goes in `adapters/`. Only `composition/` and tests import
   `@get-modular/*`.
3. A module is flat files in its feature's `composition/`: `<module>.declaration.ts` imports only
   `declareModule`, the cardinality helpers and contract descriptors, and holds only the declaration;
   `<module>.module.ts` holds only the `implement<FeatureMap>()(...)` wiring that builds the port from use
   cases and adapters. Stay within the lint size limits.
4. Implement ports as factory functions that return objects of arrow functions. Use a class only for a
   stateful adapter or a test fake: arrow-function fields, never prototype methods on a port, and
   `static async create` for async setup. `smoke` and `isolate` fail on prototype methods.
5. Port types belong to the contract owner (`contracts/`, or `application/ports/` for ports only its own
   use cases need) and use function-typed properties (`readonly run: (x: X) => Y`), never method
   signatures or a type inferred from an implementation such as `ReturnType<...>`. Descriptors live in
   `composition/<feature>.contracts.ts`. Change a contract in place: raise its `revision` and update every
   provider, consumer, fake and suite in the same change.
6. Add a module with one line in `composition/<feature>.group.ts`, one member per line, sorted; a
   parent's group also lists its sub-features' groups. A root's `modules` lists top-level feature groups
   and the root's own entries named in `roots`, nothing else; never build a list conditionally, a variant
   is a separate root with its own `profileId`. Use another feature only through its contracts (a slot),
   and only a feature you can see: your sub-features, your ancestors, and the siblings of you and of your
   ancestors. Never import its modules, groups, use cases or adapters, never reach into its sub-features,
   and never create a dependency cycle between features (using an ancestor's contracts does not count).
7. Every capability a module or input provides is one line in its feature's oracle part
   (`<feature>.wiring.ts` in the feature's test directory, whose path mirrors the feature's path).
   `optional`, `many` and several-provider slots
   get an explicit row in the root's `bindings` and in the oracle. Write the oracle from the decision;
   never copy `describeWiring` or test output into it. Each module gets an `isolate` test, and a contract
   with two implementations gets its owner's contract suite.
8. A new feature starts with the feature card in its `README.md`. Before you add a module, read the card
   and the growth report: at about 12 modules, 20 use cases, two aggregates with independent invariants
   or lifecycles, or parts that change for different reasons, first split the feature with one of the
   guide's two recipes: extract a sub-feature for a tightly bound part, or split into sibling features
   for independent parts. Past three levels of nesting the report warns; prefer siblings there.
9. Never use decorators, runtime discovery or dynamic imports of modules in production code, `any` or
   casts in wiring, registries or service bags as inputs, or closures over per-instance data or a scope.
   Upgrade Get Modular with its codemod on a clean tree
   (`pnpm --dir <get-modular checkout> codemod <from>-<to> . --write`), then typecheck and run the smoke
   and oracle tests.

<repository mapping>
```
